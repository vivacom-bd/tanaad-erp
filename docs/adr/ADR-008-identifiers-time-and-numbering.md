# ADR-008: Identifiers, time, business day and document numbering

**Status:** Accepted, 2026-11-09.

## Decision

1. **UUIDv7 for every id**, generated by the client for events created offline and by the server otherwise. Time-ordered, so indexes stay compact and ids sort by creation.
2. **Two timestamps on every event:** `occurred_at` (client clock, may be hours old) and `received_at` (server clock). Business logic uses `occurred_at`; sync uses `seq`, a server sequence assigned at append.
3. **Business timezone `Africa/Kampala`.** Stored as `timestamptz`; the API emits ISO 8601 with offset.
4. **Business day** is derived from `occurred_at` and the site's shift table: a night shift belongs to the calendar day on which it started. The server-side `Calendar` mirrors the prototype's selectors so both compute the same shift id.
5. **Document numbers** (delivery notes, invoices, vouchers, receipts) come from `number_series` per site and kind, allocated with a row lock inside the command transaction. Prefix and starting number are configurable so a site continues its paper book's sequence. Offline clients show a provisional reference; the final number is assigned at ingestion.
6. **Client clock skew** beyond 24 hours ahead of the server is rejected with `invalid_payload`; devices send their clock in the heartbeat so skew is visible.

## Alternatives

- Database `bigserial` ids: cannot be generated offline. Rejected.
- Assigning document numbers on the device: produces collisions between devices. Rejected.

## Consequences

- Reports group by business day, never by calendar date of `received_at`.
- The frontend must display provisional references distinctly until the server assigns the number.
